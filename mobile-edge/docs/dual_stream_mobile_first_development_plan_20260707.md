# 双视频流协同采集的手机优先开发方案

日期：2026-07-07  
目标：根据“双视频流：手机屏幕流 + 眼镜第一视角流”的新对齐，确定手机端、电脑端、眼镜端如何协同开发，并规定性能和理解目标。

## 1. 对齐结论

现在系统定义更清晰了：

```text
手机软件
  -> 捕获用户正在刷的手机屏幕流
  -> 接收/管理眼镜第一视角流
  -> 负责会话控制、用户反馈、轻量微卡展示

眼镜第一视角
  -> 采集过程状态：是否真在看手机、是否放一边自动播放、是否转纸笔/课本/电脑

电脑端软件
  -> 可用时作为边缘服务器
  -> 做重视频理解、双流融合、证据卡、微任务生成
  -> 结果回传手机端
```

但必须修正一点：**不能假设电脑永远在场。**  
所以架构必须是“手机优先，电脑增强”：

```text
手机端 = 永久在线入口 + 会话中枢 + 轻量处理 + 反馈端
电脑端 = 高性能边缘分析节点，可在线也可离线补分析
眼镜端 = 第一视角采集节点，优先连手机，条件允许再直连电脑
```

## 2. 为什么不能做成“电脑中心架构”

如果架构是：

```text
手机/眼镜 -> 电脑 -> 手机反馈
```

它的问题是：

| 问题 | 后果 |
|---|---|
| 学生日常不一定开电脑 | 系统只在少数场景可用 |
| 手机和电脑不一定同一网络 | 实时链路断 |
| 眼镜不一定能直连电脑 | 设备协同复杂 |
| 电脑不在场时没有反馈 | 手机端体验断裂 |

因此真实可用架构应是：

```text
手机端先运行
  -> 能独立做轻量事件和低打扰反馈
  -> 电脑在场时把重任务交给电脑
  -> 电脑不在场时缓存片段和事件
  -> 之后同步到电脑做高质量复盘
```

## 3. 三端职责

### 3.1 手机端 App

手机端是核心，不是附属端。

必须承担：

| 模块 | 作用 |
|---|---|
| Session Manager | 开始/暂停/停止采集，会话授权，隐私提示 |
| Screen Capture | MediaProjection采集手机屏幕流 |
| Surface Classifier | 判断当前是否短视频、评论、消息、搜索、图文、直播、隐私界面 |
| Dwell Tracker | 计算停留、划走、划回、复看、快速跳过 |
| Glasses Connector | 接眼镜第一视角流或事件 |
| Lightweight Event Engine | 生成轻量segment、view_relation、降级事件 |
| Local Queue | 电脑不在线时缓存事件和短片段 |
| Feedback UI | 展示兴趣探索卡、稍后列表、关闭/不感兴趣/继续了解 |
| Sync Client | 发现电脑端，推送事件/片段，接收分析结果 |

手机端必须先做到：即使没有电脑，也能记录基本兴趣流和过程流。

### 3.2 眼镜端

眼镜端不做复杂理解，优先做采集和低级事件。

必须承担：

| 模块 | 作用 |
|---|---|
| First-person Camera | 采集第一视角 |
| Timestamp Sync | 与手机同步时间 |
| Low-level Metadata | 电量、连接质量、帧率、是否遮挡 |
| Stream Sender | 低延迟发给手机，或条件允许发给电脑 |

眼镜端可以有两种形态：

| 形态 | 第一阶段可行性 |
|---|---|
| 真智能眼镜 | 后续硬件到位再做 |
| 手机B/运动相机模拟第一视角 | 第一阶段先做，验证过程证据价值 |

### 3.3 电脑端

电脑端是高性能分析节点，不是唯一入口。

必须承担：

| 模块 | 作用 |
|---|---|
| Edge Receiver | 接收手机推送的屏幕片段、眼镜片段、事件 |
| Stream Processor | 抽帧、去重、分段、对齐 |
| VLM Worker | 重视频理解，抽兴趣原子 |
| Fusion Engine | 融合手机屏幕流和第一视角流 |
| Evidence Store | 保存证据索引、关键帧、低置信降级 |
| Microtask Generator | 生成兴趣探索卡，而非直接学习任务 |
| Return Channel | 把结果回传手机 |
| Review Dashboard | 电脑在场时用于复盘、教师查看、调试 |

## 4. 数据流架构

推荐主链路：

```text
手机屏幕流
  -> 手机端实时分段/dwell/界面状态
  -> 关键帧/短片段/事件
  -> 手机本地队列
  -> 电脑端重理解
  -> 手机端微卡反馈

眼镜第一视角流
  -> 手机端接入
  -> phone_in_view / unattended_autoplay / transition_to_paper
  -> 手机本地队列
  -> 电脑端融合
  -> 手机端微卡或复盘提示
```

条件允许时可走低延迟实时链路：

```text
手机屏幕流 -> WebRTC/RTSP -> 电脑
眼镜第一视角 -> 手机转发或直连电脑 -> 电脑
电脑分析结果 -> WebSocket/DataChannel -> 手机
```

电脑不在场时走降级链路：

```text
手机端轻量分段
  -> 本地生成低置信兴趣候选
  -> 不做重VLM
  -> 只展示“稍后探索/收藏”类低打扰卡
  -> 等电脑可用后补分析
```

## 5. 两股视频流怎么处理才不会炸性能

不能把两路视频都全量实时传给电脑再每帧理解。必须分层：

| 层 | 手机屏幕流 | 第一视角流 | 处理位置 |
|---|---|---|---|
| 原始流 | 环形缓冲30-60秒 | 环形缓冲30-60秒 | 手机/眼镜本地 |
| 感知流 | 2-5fps判断切换/界面 | 2-5fps判断手机是否在视野 | 手机端 |
| 关键帧 | 0.5-1fps | 0.5-1fps | 手机端抽样 |
| 片段流 | 只保留停留>8秒或复看片段 | 只保留与手机片段重叠片段 | 发电脑 |
| VLM任务 | 只对候选片段 | 只做过程状态辅助 | 电脑端 |

核心规则：

1. 采集不等推理。
2. 队列满了丢帧，不阻塞刷视频。
3. 眼镜流不做内容主理解，只做过程关系。
4. 电脑不在线时不强求实时理解。
5. 所有输出必须绑定时间窗和证据帧。

## 6. 如何真正理解视频内容

“真的理解视频”不是等完整视频播完后写摘要，而是分阶段理解：

### 6.1 增量理解

```text
0-3秒：只判断是不是有效视频，不理解
3-8秒：生成视觉指纹和低置信兴趣候选
8-20秒：抽关键帧、OCR/ASR辅助、VLM生成兴趣原子
20秒以上/复看：提高置信，形成稳定兴趣原子
划走/结束：形成 finalized_segment
```

### 6.2 理解输出不是摘要

电脑端 VLM 不输出“这个视频讲了什么”这种泛摘要，而输出：

```json
{
  "segment_id": "seg_001",
  "content_atoms": [
    {
      "type": "concept",
      "text": "可探索概念",
      "evidence": ["screen_keyframe_001", "ocr_line_002"],
      "confidence": 0.68
    },
    {
      "type": "question",
      "text": "可追问问题",
      "evidence": ["screen_keyframe_003"],
      "confidence": 0.61
    }
  ],
  "stage": "stable_interest_atom",
  "not_full_summary": true
}
```

### 6.3 双流融合后再决定是否生成任务

| 手机内容理解 | 眼镜过程证据 | 决策 |
|---|---|---|
| 内容清晰、停留长 | 手机在视野中心、头部稳定 | 可生成兴趣探索卡 |
| 内容清晰、停留长 | 手机放一边/人看别处 | 降级，不生成卡 |
| 内容清晰、快速划走 | 眼镜看到连续滑动 | 只记录筛选，不理解 |
| 视频停留后转纸笔 | 眼镜看到书写/课本 | 可生成“承接发生”证据 |
| 进入消息/隐私 | 眼镜也看到私密场景 | 停止理解 |

## 7. 微任务如何真正生成

微任务不能由单一视频片段直接生成。必须经过四级门：

```text
内容门：视频片段里有稳定兴趣原子
行为门：用户停留/复看/收藏/搜索等行为成立
过程门：眼镜证据显示用户确实在看或后续转入学习现场
打扰门：当前适合低打扰反馈
```

只有四级门都过，才生成微任务。

微任务分三类：

| 类型 | 触发 | 例子 |
|---|---|---|
| Interest Note | 内容有兴趣原子，但过程证据一般 | “已记录一个可稍后探索的概念” |
| Exploration Card | 内容清晰 + 真实观看 + 停留足够 | “这个视频里的某个概念可以稍后了解” |
| Bridge Task | 兴趣原子与当前学习任务/纸笔承接相关 | “这个表达可以加入作文素材整理” |

默认只生成前两类。`Bridge Task` 必须更谨慎，因为它已经接近学习任务。

## 8. 性能目标

### 8.1 手机端

| 指标 | 目标 |
|---|---:|
| 采集对滑动体验影响 | 无明显卡顿 |
| Surface分类延迟 | P95≤800ms |
| Dwell事件延迟 | P95≤1.5s |
| 本地关键帧抽样 | 0.5-1fps |
| 手机端CPU额外占用 | 目标≤20% |
| 本地缓存 | 默认30-60秒环形缓冲 |
| 电脑不在线时 | 不丢事件，重分析延后 |

### 8.2 眼镜流

| 指标 | 目标 |
|---|---:|
| 手机是否在视野内识别 | ≥90% |
| 放一边自动播放识别 | ≥80% |
| 转纸笔/课本/电脑识别 | ≥80% |
| 隐私/消息漏检 | 0容忍 |
| 与手机屏幕流对齐误差 | ≤1秒，弱场景≤2秒 |

### 8.3 电脑端

| 指标 | 目标 |
|---|---:|
| 双流片段对齐 | P90≤1.5秒 |
| VLM候选生成 | 5-30秒 |
| VLM队列最大积压 | ≤3个片段 |
| 兴趣卡证据绑定率 | 100% |
| 非视频/隐私误生成卡 | 0 |
| 微卡回传 | 分析完成后≤2秒 |

## 9. 开发路线

### Phase 0：USB验证

目标：先证明手机屏幕流可抓、可分段。

交付：

- scrcpy真实浏览样本；
- 20个segment人工复核；
- 停留/划走/划回日志。

### Phase 1：手机端原型

目标：做真正手机App雏形。

模块：

- MediaProjection采屏；
- Session Manager；
- Surface Classifier；
- Dwell Tracker；
- Local Queue；
- Feedback UI雏形。

### Phase 2：第一视角模拟

目标：先不用真眼镜，用手机B/运动相机模拟。

模块：

- 第一视角视频采集；
- 手机是否在视野内；
- 放一边自动播放；
- 转纸笔/课本/电脑；
- 与手机屏幕流时间对齐。

### Phase 3：电脑端边缘分析

目标：电脑端做重处理。

模块：

- FastAPI/WebSocket接收；
- 片段存储；
- 双流对齐；
- VLM Worker；
- Fusion Engine；
- Microtask Generator；
- 手机回传。

### Phase 4：手机-电脑互联

目标：手机发现电脑，能实时或准实时发送片段并接收微卡。

推荐：

- 同一局域网：WebSocket/WebRTC；
- 不同网络：先不做，后续再考虑云中继；
- 电脑不在线：手机本地排队，延后同步。

### Phase 5：眼镜真实接入

目标：替换模拟第一视角设备。

优先路线：

- 眼镜 -> 手机：蓝牙/Wi-Fi/厂商SDK；
- 手机 -> 电脑：WebSocket/WebRTC；
- 条件允许时眼镜 -> 电脑直连作为增强，不作为唯一路线。

## 10. 为什么这个方案能克服“用户不用电脑”

答案是：电脑不是入口，手机才是入口。

| 场景 | 系统处理 |
|---|---|
| 学生只拿手机刷 | 手机端记录轻量事件和低置信兴趣候选 |
| 电脑在旁边且在线 | 手机把候选片段发给电脑重分析 |
| 电脑不在线 | 手机本地缓存，稍后同步 |
| 眼镜在线 | 手机融合第一视角过程证据 |
| 眼镜不在线 | 回退到手机屏幕流基础链路 |
| 两者都在线 | 生成高质量双流证据卡 |

这样系统不会因为电脑不在场就完全失效。

## 11. 当前架构评分

当前架构评分：**8/10**。

已经清晰的部分：

1. 双视频流职责分清：手机流负责内容，眼镜流负责过程。
2. 手机是会话中枢，电脑是增强算力，解决电脑不常用的问题。
3. 微任务生成经过内容门、行为门、过程门、打扰门。
4. 支持电脑不在线时降级缓存。

还没到10/10的原因：

1. 真实手机App尚未开发，MediaProjection性能未实测。
2. 眼镜真实设备链路未确定，目前只能用手机B/运动相机模拟。
3. VLM模型选型和本机推理性能未实测。
4. 手机端本地轻量模型能力边界未实测。

## 12. 一句话定版

系统不是“手机和眼镜都把视频扔给电脑总结”，而是：

> 手机App作为持续在线的会话中枢，直接捕获手机屏幕兴趣流，并接入眼镜第一视角过程流；电脑端在可用时承担重视频理解和双流融合，生成有证据、有降级、有打扰控制的兴趣探索卡或桥接任务，再回传手机。电脑不在线时，手机端保留轻量事件和缓存，系统降级但不断链。
