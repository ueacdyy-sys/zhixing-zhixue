# 实时捕获与兴趣探索性能指标

日期：2026-07-07  
用途：定义手机授权实验后的性能门槛，避免系统只做到“能录屏”，却不适合真实刷视频场景。

## 1. 核心结论

这个系统成立的前提不是“能看到手机画面”，而是同时满足四件事：

1. 用户正常刷视频时不明显卡顿。
2. 系统能识别当前可见内容段和停留时长。
3. 系统能从视频内容里抽出兴趣线索，而不是立刻生成正式学习任务。
4. 生成的东西是“兴趣探索卡”，不是强行拉人学习的课程/题目/知识点任务。

第一阶段实验只要有一项不达标，就不能进入正式Android App开发。

## 2. 刷视频停留分层

下面不是行业绝对平均值，而是本项目第一阶段的工程阈值。真实阈值要用样本复核后校准。

| 停留区间 | 行为解释 | 系统处理 |
|---|---|---|
| < 1.2 秒 | 快速划走/无效曝光 | 只记录 `skip_flag=true`，不做VLM，不生成卡片 |
| 1.2-3 秒 | 短暂扫过 | 抽1帧做低成本指纹，只用于相似内容统计 |
| 3-8 秒 | 初步兴趣 | 做关键帧embedding，可进入候选兴趣事件，不主动打扰 |
| 8-20 秒 | 明显停留 | 异步调用轻量VLM，生成兴趣探索候选卡 |
| > 20 秒 | 强停留/完整观看倾向 | 生成高置信兴趣事件，可低频回传“稍后探索”卡 |
| 重复出现/复看 | 同类兴趣稳定 | 提升兴趣权重，但仍不直接转正式学习任务 |

原则：停留越短，处理越轻；停留越长，语义理解越深。系统不能因为一个短曝光就推任务。

## 3. 体验性能指标

| 指标 | Phase 0 USB/scrcpy目标 | Phase 1 无线/软件流目标 | 不达标处理 |
|---|---:|---:|---|
| 用户可感知卡顿 | 无明显滑动卡顿 | 无明显滑动卡顿 | 降采样、降码率、停止推理 |
| PC端画面延迟 | ≤300ms优先，≤700ms可接受 | ≤1.5s可接受 | 只保留离线样本，不做准实时回传 |
| 有效画面比例 | ≥90% | ≥80% | 黑屏/遮挡记录为 `capture_low_quality` |
| 采集稳定时长 | 连续10分钟不中断 | 连续10分钟不中断 | 不进入下一阶段 |
| 手机额外CPU占用 | 目标≤15% | 目标≤20% | 降帧、降分辨率 |
| 手机温升/发热 | 10分钟内不明显烫手 | 10分钟内不明显烫手 | 停止长时实验 |
| PC处理队列延迟 | P95 ≤5秒 | P95 ≤10秒 | 丢帧，不阻塞采集 |
| 微卡回传延迟 | 停留结束后5-30秒 | 停留结束后5-45秒 | 转为“稍后复盘”，不实时提示 |

体验优先级高于理解完整度：宁可少理解几个片段，也不能影响用户刷视频。

## 4. 实时数据流处理规则

实时流不能按“每帧都理解”处理，必须分层。

```text
手机屏幕流
  -> 低延迟接收
  -> 环形缓冲 30-60 秒
  -> 内容切换检测 2-5 fps
  -> 稳定段判定
  -> dwell tracker
  -> 关键帧抽样 0.5-1 fps
  -> embedding/指纹
  -> 候选段筛选
  -> 轻量VLM异步理解
  -> 兴趣探索卡候选
  -> 手机轻量回传/稍后队列
```

队列规则：

| 队列 | 最大积压 | 超限处理 |
|---|---:|---|
| 原始帧队列 | 3-5帧 | 丢旧帧 |
| 关键帧队列 | 20帧 | 合并相似帧 |
| VLM任务队列 | 3个片段 | 只保留停留更久、重复更高、内容更清晰的片段 |
| 回传队列 | 5张卡 | 合并为“稍后探索列表” |

硬规则：推理线程永远不能反向阻塞采集线程。

## 5. 视频理解输出要求

视频理解不是泛摘要，也不是课程推荐。每个候选片段只抽以下字段：

```json
{
  "segment_id": "seg_001",
  "dwell_ms": 12600,
  "content_atoms": {
    "words_or_expressions": ["词语/表达"],
    "concepts": ["概念"],
    "phenomena": ["现象"],
    "persons_or_objects": ["人物/对象"],
    "conflicts_or_questions": ["观点冲突/可追问问题"]
  },
  "exploration_angle": "可以继续了解的角度",
  "confidence": 0.0,
  "evidence_keyframes": ["frames/seg_001_001.jpg"],
  "downgrade_reason": null
}
```

禁止输出：

- “你应该现在学习某知识点”
- “给你推一道题”
- “进入课程”
- “该学生对某学科有能力/人格/心理判断”
- 没有证据帧的确定性解释

允许输出：

- “这个视频里出现了一个可以稍后了解的词/概念”
- “这里有一个观点冲突，可以收藏到稍后探索”
- “这个表达可以和作文素材/阅读理解/项目资料建立弱关联”
- “证据不足，只记录为兴趣曝光”

## 6. 微任务不是正式学习任务

本系统在手机刷视频场景中生成的不是学习任务，而是兴趣探索卡。

| 类型 | 触发条件 | 用户感受 | 示例 |
|---|---|---|---|
| 记录卡 | 停留3-8秒或低置信 | 不打扰，只进稍后列表 | “记录到一个可能的兴趣点” |
| 探索卡 | 停留8-20秒，内容清晰 | 可关闭、可稍后 | “这个视频里的‘某概念’可以稍后了解一下” |
| 迁移卡 | 重复停留或与当前任务弱相关 | 轻量建议，不强推 | “这个表达可作为作文/阅读材料例子” |
| 复盘卡 | 多次兴趣未承接或中断 | 任务后查看 | “今天有3个兴趣点未继续探索” |

微任务字段：

```json
{
  "microtask_id": "mt_001",
  "source_segment_id": "seg_001",
  "type": "interest_exploration",
  "title": "稍后了解：一个可追问概念",
  "prompt": "这个内容里出现了一个值得继续了解的问题，要不要稍后看看？",
  "actions": ["later", "save", "dismiss", "not_interested", "explore_now"],
  "interruption_level": "low",
  "expires_at": "session_end_or_24h",
  "linked_learning_task": null
}
```

关键边界：`linked_learning_task` 默认是 `null`。只有用户接受、重复出现、或与当前学习任务明确相关时，才允许转入学习流。

## 7. 实时生成节奏

| 时机 | 系统动作 |
|---|---|
| 视频刚出现0-1秒 | 只检测画面是否稳定 |
| 1-3秒 | 判断是否快速划走 |
| 3-8秒 | 生成内容指纹，不提示 |
| 8秒以后 | 异步理解，生成候选探索卡 |
| 用户划走后 | 根据完整停留段决定是否保留 |
| 结果出来时用户还在刷 | 低频轻提示或进入稍后列表 |
| 用户连续关闭 | 提高打扰成本，停止主动提示 |

最低要求：微任务不追求毫秒级实时，追求“用户不被打断”。兴趣探索卡允许滞后，甚至允许只在任务后/当天复盘时出现。

## 8. Go/No-Go 性能门槛

| 门槛 | 通过标准 |
|---|---|
| G1 屏幕流成立 | 10分钟真实浏览，有效画面比例≥90%，不卡顿 |
| G2 停留分段成立 | 人工复核20段，停留/划走/复看判断可用率≥80% |
| G3 低成本处理成立 | 短停留段不进VLM，队列不积压，采集不中断 |
| G4 兴趣理解成立 | 候选片段能抽出概念/表达/现象/人物/问题，不是泛摘要 |
| G5 微任务边界成立 | 生成的是兴趣探索卡，默认不转正式学习任务 |
| G6 低打扰成立 | 用户连续关闭后系统能停止主动提示 |

如果 G1-G3 不过，停止技术推进，回到采集链路。  
如果 G4-G6 不过，说明不是捕获问题，而是语义和交互策略问题，不能拿来展示完整闭环。

## 9. 手机授权后的实验顺序

1. ADB授权，只验证设备连通。
2. scrcpy镜像，只验证真实屏幕流和体验。
3. 录制10分钟样本，只做画面质量和停留分段。
4. 抽关键帧和embedding，不急着生成微任务。
5. 人工复核停留段，确认阈值。
6. 对少量高停留片段做VLM理解。
7. 只生成兴趣探索卡，不生成正式学习任务。
8. 再考虑无线ADB、ScreenStream、MediaProjection/WebRTC正式路线。

## 10. 一句话约束

这个系统不是“刷到视频就让学生学习”，而是：

> 在不打断刷视频体验的前提下，识别学生自然停留过的内容里有哪些可被稍后探索的词语、概念、表达、现象、人物或问题，并把它们作为可撤回、可关闭、可复盘的兴趣证据。
