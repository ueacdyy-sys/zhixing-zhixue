# 场景反推的实时短视频理解设计

日期：2026-07-07  
用途：从真实刷短视频场景反推技术路线、状态机、防呆设计和性能目标。  
边界：本文不修改原方案；它用于约束后续手机授权实验。

## 1. 先定边界：NotebookLM 不是同一类问题

Google NotebookLM 可以导入公开 YouTube URL，但官方帮助说明只支持带字幕的公开视频，并且导入的是视频文本转写，而不是实时视频流本身。它解决的是“把已有材料作为 source 做理解”，不是“用户正在手机上刷什么、看多久、是否划回、是否进了消息页、是否应该低打扰生成兴趣探索卡”。

所以本项目不能对标 NotebookLM 的处理方式。我们的目标是：

```text
当前屏幕
  + 实时行为
  + 内容线性展开
  + 停留/划走/划回/复看
  + 场景防呆
  -> 增量兴趣理解
  -> 低打扰兴趣探索卡
```

核心区别：

| 对比项 | NotebookLM类处理 | 本项目必须处理 |
|---|---|---|
| 输入 | 公开URL、文件、音频、转写文本 | 手机当前屏幕流 |
| 时间性 | 材料已存在，可整体理解 | 视频线性展开，没播完前只能增量理解 |
| 用户行为 | 基本不处理观看行为 | 必须处理停留、划走、划回、复看、暂停、进评论、看消息 |
| 输出 | 摘要、问答、笔记 | 兴趣探索证据、微卡、稍后复盘 |
| 场景风险 | source质量问题 | 把非视频当视频、把消息当学习兴趣、打扰刷视频体验 |

## 2. 正确问题不是“理解视频”，而是“边看边形成可修正的兴趣假设”

真实视频是线性的。系统在视频没播完之前不能假装知道完整主题，只能像人一样形成临时理解，并随着后续画面、字幕、音频、用户行为不断修正。

因此理解对象不是一个最终摘要，而是一个会变化的 `hypothesis_ledger`：

```json
{
  "segment_id": "seg_001",
  "stage": "partial",
  "observed_ms": 8600,
  "current_hypotheses": [
    {
      "type": "concept",
      "text": "暂定概念",
      "evidence": ["keyframe_001", "ocr_line_002"],
      "confidence": 0.46,
      "status": "provisional"
    }
  ],
  "revisions": [
    {
      "ts": "2026-07-07T16:20:10+08:00",
      "from": "人物故事",
      "to": "电影解说中的人物评价",
      "reason": "后续字幕和画面修正"
    }
  ]
}
```

系统输出必须允许三种状态：

| 状态 | 含义 | 是否能生成微卡 |
|---|---|---|
| `provisional` | 临时理解，证据还少 | 不主动提示，只记录 |
| `stable_interest_atom` | 已有稳定兴趣原子 | 可进入候选卡 |
| `finalized_segment` | 用户划走/片段结束后形成阶段结论 | 可生成稍后探索卡 |

关键规则：**实时理解不能等同于实时下结论。**

## 3. 真实短视频场景状态机

在做视频理解之前，必须先判断用户现在处于什么界面。否则会把消息、评论、搜索、个人主页、广告、直播、图文贴都错当成短视频。

### 3.1 顶层状态

```text
UNKNOWN
  -> SHORT_VIDEO_FEED
  -> VIDEO_DETAIL_OR_FULL_SCREEN
  -> COMMENT_PANEL
  -> MESSAGE_OR_CHAT
  -> SEARCH_OR_DISCOVERY
  -> PROFILE_OR_CREATOR_PAGE
  -> LIVE_STREAM
  -> AD_OR_SHOP
  -> IMAGE_TEXT_POST
  -> SYSTEM_OVERLAY
  -> OUT_OF_SCOPE_APP
  -> PRIVATE_OR_SENSITIVE
```

只有以下状态允许进入视频内容理解：

| 状态 | 是否理解视频 | 处理 |
|---|---|---|
| `SHORT_VIDEO_FEED` | 是 | 正常处理 |
| `VIDEO_DETAIL_OR_FULL_SCREEN` | 是 | 正常处理 |
| `LIVE_STREAM` | 限制处理 | 只做短窗口兴趣原子，不做完整结论 |
| `AD_OR_SHOP` | 降级处理 | 默认不生成学习卡，只记录广告/购物内容 |
| `IMAGE_TEXT_POST` | 不是视频 | 转为图文兴趣候选，不走视频停留逻辑 |
| `COMMENT_PANEL` | 否 | 只记录用户进入评论区，不理解评论内容 |
| `MESSAGE_OR_CHAT` | 否 | 隐私保护，停止内容理解 |
| `SEARCH_OR_DISCOVERY` | 否/弱处理 | 只记录搜索行为，不把结果页当视频 |
| `PROFILE_OR_CREATOR_PAGE` | 否/弱处理 | 只记录访问创作者页 |
| `SYSTEM_OVERLAY` | 否 | 暂停当前片段计时 |
| `PRIVATE_OR_SENSITIVE` | 否 | 停止采集或遮罩 |

### 3.2 先判界面，再判内容

系统管线必须是：

```text
screen_frame
  -> surface_classifier
  -> privacy_guard
  -> video_eligibility_gate
  -> transition_tracker
  -> dwell_tracker
  -> content_understanding
```

不能是：

```text
screen_frame -> VLM -> 总结视频
```

因为后者会把所有画面都当视频来理解。

## 4. 必须模拟的真实用户操作

第一阶段实验不能只测“往下刷”。至少要覆盖下面这些操作。

| 操作 | 风险 | 系统应对 |
|---|---|---|
| 上滑到下一个视频 | 新片段开始 | 结束旧segment，开启新segment |
| 下滑回上一个视频 | 不是新兴趣，可能是复看 | 用视觉指纹匹配旧segment，`revisit=true` |
| 半滑又回弹 | 不是有效切换 | 不结束segment，标记 `swipe_cancelled` |
| 快速连续滑动 | 用户在筛选 | 只记录跳过，不进VLM |
| 停在视频但没看完 | 只能增量理解 | 生成 provisional hypothesis |
| 视频自动循环 | 可能是复看，也可能只是没滑走 | 识别画面周期，避免重复算多个新segment |
| 暂停视频 | 可能是认真看/读字幕/离开 | 暂停态单独记录，不直接判兴趣 |
| 打开评论区 | 不再是视频主画面 | 停止视频理解，只记录 `open_comment` |
| 关闭评论区回到视频 | 恢复旧segment | 继续原segment或建立 child_segment |
| 打开消息/回复消息 | 隐私场景 | 进入 `MESSAGE_OR_CHAT`，停止内容理解 |
| 搜索内容 | 学习/兴趣信号可能强 | 记录搜索行为，但不按视频处理 |
| 进入创作者主页 | 兴趣延伸信号 | 记录 creator_interest，不理解私密内容 |
| 看直播 | 无明确结束点 | 只做滑动窗口理解，不做最终摘要 |
| 看广告/购物卡 | 容易误触发 | 默认不生成学习探索卡 |
| 图文/图片贴 | 不是视频 | 进入图文理解分支 |
| 通知弹窗/系统控制中心 | 遮挡 | 暂停计时，遮罩或丢弃帧 |
| 切出App/锁屏 | 会话中断 | 结束或暂停session |

这些不是边缘情况，而是真实刷短视频时的常规操作。

## 5. 防呆设计

### 5.1 不把非视频当视频

必须有 `video_eligibility_gate`，输出四类：

| 输出 | 含义 | 后续 |
|---|---|---|
| `eligible_video` | 明确是视频主画面 | 进入dwell和视频理解 |
| `eligible_live_window` | 直播/长流 | 只做滑动窗口兴趣原子 |
| `non_video_surface` | 评论、消息、搜索、主页、图文 | 不进视频VLM |
| `ambiguous_surface` | 不确定 | 只记录低置信事件，不生成卡 |

第一阶段验收：非视频误判为视频的比例必须低于 5%；涉及消息/隐私界面时，误进入内容理解的容忍度为 0。

### 5.2 不把消息当兴趣内容

只要识别到以下特征之一，就进入 `PRIVATE_OR_SENSITIVE` 或 `MESSAGE_OR_CHAT`：

- 聊天列表/对话气泡布局；
- 输入框和键盘出现；
- 通讯录/私信页；
- 账号、手机号、二维码、支付、地址等敏感信息；
- 系统通知展开。

处理规则：停止内容理解，只保留“用户从视频转入消息/私密界面”的行为事件；原始帧不进入展示包。

### 5.3 不把“划回上一个视频”当新视频

每个片段必须生成视觉指纹：

```json
{
  "segment_id": "seg_018",
  "fingerprint": "embedding_cluster_abc",
  "revisit_of": "seg_014",
  "revisit_confidence": 0.83,
  "direction": "swipe_down_return"
}
```

如果新片段和过去60秒内片段相似度高，就标记为 `revisit`，不是新兴趣。复看可以提高兴趣强度，但不能重复生成卡。

### 5.4 不把“刚刷到”当“想学习”

微卡触发必须同时满足：

1. `surface_state=SHORT_VIDEO_FEED` 或 `VIDEO_DETAIL_OR_FULL_SCREEN`。
2. `dwell_ms >= 8000`，或重复出现/复看。
3. 有至少一个稳定兴趣原子。
4. 当前没有评论、消息、搜索、通知遮挡。
5. 过去一段时间没有连续关闭/拒绝。
6. 微卡类型是兴趣探索，不是正式学习任务。

## 6. 实时理解策略：从“帧”到“兴趣原子”

视频没播完之前，系统不能直接总结主题。正确做法是把视频理解拆成四层：

| 层 | 时间要求 | 输出 | 作用 |
|---|---:|---|---|
| 感知层 | 100-300ms | 是否可见、是否遮挡、是否切换 | 保证不卡 |
| 场景层 | 300-800ms | 当前界面状态 | 防止误判 |
| 行为层 | 0.5-1.5s | 停留、划走、划回、复看、暂停 | 判断兴趣强度 |
| 语义层 | 5-30s | 词语、概念、表达、现象、人物、问题 | 生成兴趣探索 |

这意味着实时系统不是所有模块都实时。真正需要低延迟的是感知、场景和行为；语义可以滞后。

### 6.1 增量理解窗口

推荐使用三个窗口：

| 窗口 | 长度 | 用途 |
|---|---:|---|
| `micro_window` | 1-3秒 | 判断画面稳定、切换、遮挡 |
| `interest_window` | 8-20秒 | 抽兴趣原子 |
| `review_window` | session结束或任务后 | 生成复盘证据 |

实时微卡只能来自 `interest_window`，不能来自 `micro_window`。

### 6.2 兴趣原子

兴趣原子不是知识点，也不是任务。它只表示“这个内容中有一个可以稍后探索的对象”：

```json
{
  "atom_id": "atom_001",
  "atom_type": "concept | word | expression | phenomenon | person | conflict | question",
  "text": "候选内容",
  "source_segment_id": "seg_001",
  "evidence": ["keyframe_001", "ocr_002", "asr_003"],
  "confidence": 0.62,
  "status": "stable_interest_atom",
  "learning_transfer": {
    "allowed": false,
    "reason": "needs_user_acceptance_or_context_match"
  }
}
```

默认不能直接迁移到语文学习或正式任务。必须经过用户接受、重复兴趣、或当前任务上下文匹配。

## 7. 微任务生成规则

本项目在刷视频场景里生成的是“兴趣探索卡”，不是“学习任务”。

### 7.1 触发等级

| 等级 | 条件 | 输出 |
|---|---|---|
| L0 | <3秒快速划走 | 不输出 |
| L1 | 3-8秒，有低置信兴趣 | 只进稍后候选，不提示 |
| L2 | 8-20秒，兴趣原子稳定 | 生成探索卡候选 |
| L3 | >20秒或复看，内容清晰 | 可低频展示探索卡 |
| L4 | 用户主动点开/收藏/搜索 | 可生成更明确的探索卡 |

### 7.2 卡片内容边界

允许：

- “这个视频里出现了一个可以稍后了解的词。”
- “这里有一个观点冲突，可以保存到稍后探索。”
- “这个人物评价/表达方式可以作为素材线索。”

禁止：

- “现在来学这个知识点。”
- “给你推一道题。”
- “你这个地方不懂。”
- “你注意力不集中。”

### 7.3 打扰控制

| 指标 | 第一阶段目标 |
|---|---:|
| 主动提示频率 | ≤1次/3分钟 |
| 连续关闭后静默 | 至少15分钟 |
| 单次提示占屏 | 尽量轻量，不遮挡视频主体 |
| 用户无动作 | 自动进入稍后列表，不重复弹 |
| 学习任务转化 | 默认不转，必须用户接受或上下文强匹配 |

## 8. 需求反推技术，再由技术约束反推性能目标

| 需求 | 技术约束 | 性能目标 |
|---|---|---|
| 用户刷视频不能卡 | 采集和推理解耦，推理慢就丢帧 | 采集不中断；感知层P95≤300ms |
| 视频没播完不能乱下结论 | 增量假设账本，可修正 | 语义输出必须带 `provisional/finalized` 状态 |
| 用户可能划回上一个视频 | 视觉指纹和方向检测 | 划回识别准确率≥80% |
| 用户可能不是在看视频 | 先做界面状态分类 | 非视频误判视频≤5%；消息页误判容忍0 |
| 用户可能打开评论/消息 | surface_state切换和隐私保护 | 进入消息后1秒内停止内容理解 |
| 用户快速筛选视频 | 短停留段不进VLM | <3秒片段VLM调用率=0 |
| 微任务不能变正式学习 | 卡片类型和字段约束 | `linked_learning_task` 默认 null |
| 用户不想被打扰 | 打扰成本和反馈闭环 | 连续关闭后静默≥15分钟 |
| 实时理解不能等完整视频 | 滑动窗口理解 | 8秒后可形成候选兴趣原子，最终结论等片段结束 |
| 证据要可复查 | 每个输出绑定时间窗和关键帧 | 100%兴趣卡有 `segment_id/evidence` |

## 9. 新的性能目标

### 9.1 场景识别指标

| 指标 | 目标 |
|---|---:|
| 界面状态分类P95延迟 | ≤800ms |
| 视频/非视频二分类准确率 | ≥90% |
| 消息/隐私界面漏检 | 0容忍，实验样本中必须为0 |
| 系统遮挡/通知识别 | ≥90% |

### 9.2 行为识别指标

| 指标 | 目标 |
|---|---:|
| 上滑新视频识别 | ≥90% |
| 下滑划回识别 | ≥80% |
| 半滑取消识别 | ≥70%，低置信时不切segment |
| 停留时长误差中位数 | ≤0.8秒 |
| 停留时长误差P90 | ≤1.5秒 |
| 快速划走识别 | ≥90% |
| 复看/循环去重 | ≥80% |

### 9.3 实时处理指标

| 指标 | USB验证目标 | 无线/软件流目标 |
|---|---:|---:|
| 画面到PC延迟 | P95≤700ms | P95≤1.5s |
| 有效画面比例 | ≥90% | ≥80% |

| 场景层处理 | P95≤800ms | P95≤1.2s |
| VLM候选生成 | 5-30秒 | 5-45秒 |

### 9.4 微任务指标

| 指标 | 目标 |
|---|---:|
| <3秒片段生成卡片 | 0 |
| 非视频界面生成视频卡 | 0 |
| 消息/隐私界面生成卡 | 0 |
| 兴趣探索卡证据绑定率 | 100% |
| 主动提示频率 | ≤1次/3分钟 |
| 连续关闭后静默 | ≥15分钟 |
| 默认转正式学习任务 | 0 |

## 10. 实验设计必须更新

后续拿到手机授权后，不能只做“刷10分钟视频”。必须做场景脚本：

| 脚本 | 内容 | 验收点 |
|---|---|---|
| S1 正常上滑刷视频 | 连续刷20条 | 新segment、快速划走、停留 |
| S2 下滑返回 | 刷过3条后下滑回上一条 | `revisit_of` 是否正确 |
| S3 半滑取消 | 手指上滑一半又放回 | 不误切segment |
| S4 打开评论 | 看视频中打开评论区 | 停止视频理解 |
| S5 打开消息 | 从平台进入消息/私信 | 隐私保护，不理解内容 |
| S6 搜索 | 搜索一个词再看结果 | 记录搜索，不当视频 |
| S7 主页/创作者页 | 点头像进入主页 | 不当视频主画面 |
| S8 直播 | 进入直播间停留 | 滑动窗口，不做完整结论 |
| S9 广告/购物 | 点进购物/广告卡 | 不生成学习探索卡 |
| S10 通知遮挡 | 下拉通知或弹窗 | 暂停/遮罩 |
| S11 图文贴 | 浏览图片/文字内容 | 进入图文分支 |
| S12 切出App | 返回桌面/切应用 | 暂停或结束session |

只有这些脚本通过，才能说这个系统理解了真实刷短视频场景，而不是只会处理理想化视频流。

## 11. 当前系统设计评分

当前设计从 8/10 调整为 **7/10**。

降分原因：

1. 之前只定义了屏幕流和停留分段，没有完整定义短视频App状态机。
2. 没有把“非视频界面”和“隐私界面”作为硬防呆门槛。
3. 没有定义“视频没播完前只能增量理解”的数据结构。
4. 没有覆盖下滑返回、半滑取消、评论、消息、搜索、直播、广告、图文等真实操作。

补齐本文之后，进入实验前的设计目标是 **8.5/10**。要到 10/10，必须用真实手机跑完 S1-S12 场景脚本，并给出误判率、延迟、停留误差和微卡生成日志。

## 12. 一句话定准

技术路线必须服务这个场景判断：

> 系统不是拿完整视频做总结，而是在用户真实刷短视频的过程中，先判断用户到底是不是在看视频，再用低延迟行为识别和滞后语义理解，逐步形成可修正的兴趣原子；只有在停留足够、证据足够、场景合适、打扰成本可接受时，才生成可关闭、可稍后、默认不转正式学习的兴趣探索卡。
