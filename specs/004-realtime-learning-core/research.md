# 设计决策与调研结论

## D-01：实时理解与学习承接分层

**决定**：L0 使用持续 `RealtimeSemanticFact`；L1 以稳定 `SemanticScope` 的 `L1LearningBrief` 触发；L2–L4 用可增量 `ContentAnalysisPackage` 扩展。

**理由**：要求整条视频完成才通知会违背实时触达；反过来，只凭单帧或 OCR 又不能形成完整理解。以语义闭合窗口为 L1 最小单位，能够同时保持实时性和证据边界。

**拒绝方案**：

- “等播放结束再分析”：不满足用户仍在关注时介入。
- “每帧直接发概念”：无法形成可靠语义且会造成通知风暴。

## D-02：手机 UI 与数据架构

**决定**：保留 Jetpack Compose、Material 3、V5 token、Koin、MediaProjection/RTSP 语义和 PC TLS 配对；媒体 data plane 另加会话加密、双向认证、分片完整性与 anti-replay，不能把 RTSP 或局域网视为安全边界；引入 Navigation Compose、Room、ViewModel/StateFlow 与 feature 分层。

**理由**：既有 V5 的信息架构和视觉可用，问题在手写路由、service locator 和 JSON 偏好存储无法承接实时实体与原子投递。

## D-03：PC/云计算路径

**决定**：已配对 PC 只走本地模型；断连只缓存续传。无 PC 使用与 PC 同构的团队云网关接口；未部署真实网关时为 `CAPTURE_PENDING_ANALYSIS`。

**理由**：不能让配对 PC 的会话在断开时静默切云，也不能用 Android 聊天 API 假装媒体分析成功。

无 PC 是目标用户路径而非演示备选。未部署云网关时安全地显示不可用是必要降级，但只有 Android 真机完成云端授权、连续 L0、L1 和撤回删除，才能称无 PC 路径可用。

## D-04：联网知识图谱补全

**决定**：PC `KnowledgeEnrichmentAgent` 在 L1 概念锚点产生后运行，使用低优先级队列生成 `ContentGraphRevision`；外部来源作为不可信输入，保留来源、摘录、时间、版本和冲突状态。

**理由**：L2 应逐步生长；图谱补全不能阻断 L0/L1，也不能把检索结果或当前内容自动沉淀为长期画像。W3C PROV-DM 的实体—活动—代理溯源模型可作为来源/修订记录的参考。

**补充决定**：检索 fetcher 运行在无凭据沙箱，拒绝私网/metadata/DNS 重绑定、重定向逃逸、网页提示注入和自动执行附件；其失败不得回流 L0/L1。

## D-05：通知语义

**决定**：L1 学习内容生成、PC ACK、Android 系统通知投递是三件独立的事。通知被权限、频道或 OEM 抑制时，L1 仍进入发现页。

**理由**：Android 官方通知机制受运行时权限、用户频道设置与系统策略影响；`IMPORTANCE_HIGH` 只表示请求高优先级，不能把 API 调用成功描述为学生看见 heads-up。

## 尚待真实验证的事实

1. 目标 PC 模型与硬件能否在持续输入速率下保持实时水位。
2. 各目标手机/OEM 上来源过滤和 heads-up 的实际效果。
3. 眼镜的实时媒体协议、时钟、SDK 与可授权范围。
4. 团队云网关资源、凭证、数据生命周期与成本上限。
5. 目标 Android/OEM/公开媒体是否允许合法、同步的播放音频采集；不能假设可做到所有应用 100%。
6. 每个候选设备—模型配置在持续输入下的批准 SLO，以及媒体安全、episode 边界、scope 隔离和检索沙箱的负例表现。

这些是验收前提，不是可以由文档假定为已完成的能力。
